## Root causes found (traced with a scratch pytest plugin dumping stones, exemptions, groups and rows)
1. RECON-51, `identity.stored_backup`: a row stored by an earlier backup B0 and repeated unchanged by the decision
   backup B1 counted as B0's content. Holds were decided on B0 (RECON-20), the release too, so the next import of B1
   never covered it (held again; the export waited: 13075, 13159), and live (B0 imported first, h1 arm) never covered
   the row with a release decided on B1 (A5 (a): 13002, 13008, ...). Fixed: the newest 'already imported' (same source
   row) run counts for a readable row.
2. RECON-52, `groups.list_unlisted`: a released group row waiting for its text was listed again as a pending 'not in
   this backup' hold at every sweep (RECON-38). Fixed: skipped while a trusted release of that exact row for that group
   exists (`groups._release_waits`).
3. B7-restore group rows (13825, 13150, 13275, 13500, 13525, 13725, 13800, 13875, 13250 h0): the s2 hold was the
   re-listing of (2) on a row the admin released, whose next import (X) no longer held it; the restore's re-import of
   the older backup the release covers brought the released text back. The same re-import without any restore
   (scratch S1NORESTORE experiment: restore and removals skipped, same re-import list) gives the same rows readable: a
   re-import effect, not a restore durability gap. 13000's carrier: the hold for X's content was ended by the re-import
   of the older backup the release covers (also without restore).
4. A5 (b) (13010, 13098, 13351, 13815 h0): the uid key names another JARVIS row on the test copy (an earlier backup's
   row, e.g. a branch parent's copy) than on live; the test copy's own row of live's row is held because its release
   never completed under its row-form key. Live shows exactly the released text of the release of that exact row.
