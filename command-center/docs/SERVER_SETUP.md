# Connecting a CWP server (restricted SSH)

The **VPS & Server Management** and **WordPress Security & Repair** agents reach a
server over SSH, but only through **cc-gate**: a small program that is the *forced
command* of a dedicated, unprivileged account. Whatever the Command Center asks
for, the server runs cc-gate, and cc-gate only performs operations from a short
allowlist, with checked arguments, without a shell.

Nothing in this guide is done for you. You run every step on your own server,
and you decide when (or whether) changes are allowed.

## What the Command Center can and cannot do

| | |
|---|---|
| Account | a dedicated account (default `ccagent`), never root; key login only |
| Key | an Ed25519 key generated by the Command Center; the private half stays encrypted in its database and is never shown, logged or sent to an AI model |
| The key can only run | `cc-gate` (`command="/usr/local/bin/cc-gate",restrict`): no shell, no port forwarding, no SFTP/SCP, no agent or X11 forwarding |
| Read operations | system overview (uptime, load, memory, disk), service status, WordPress version, core checksum check, plugin/theme lists with updates, administrator accounts, home/siteurl, maintenance mode, debug.log presence |
| Change operations (only if you set `allow_changes: true`) | database backup, restore home/siteurl to the URL in **your** config, deactivate/activate/update/reinstall a plugin, reinstall core files (same version), maintenance mode, cache flush, move debug.log into the backup folder, restart a service you listed as restartable |
| Never | run arbitrary commands, edit files, delete anything, read wp-config.php or the database, touch sites you did not configure, use root |
| Approvals | every change waits for a person's approval in the dashboard; for production sites or servers an **admin** must type the site or server name |
| Audit | every request is recorded in the Command Center (Servers page) and in `/var/log/cc-gate/gate.log` on the server |

WP-CLI runs as each site's own system user (through sudo rules limited to WP-CLI
and the site helper), with plugins and themes skipped where possible, so a broken
plugin cannot block a repair.

## Requirements on the server

- EL8/EL9 (AlmaLinux, Rocky) with CWP, root access for the one-time setup.
- Python 3.6 or newer (always present on EL8/9 as `/usr/libexec/platform-python`).
- WP-CLI at `/usr/local/bin/wp` (install it once if missing:
  `curl -o /usr/local/bin/wp https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar && chmod 755 /usr/local/bin/wp`)
  and a PHP CLI on the PATH that WP-CLI can use.
- Your Command Center's public IP allowed to reach SSH (CSF: `csf -a <ip>`).
- Recommended sshd settings: `PasswordAuthentication no`, `PermitRootLogin no`
  (or `prohibit-password`), and if you use `AllowUsers`, add `ccagent`.

## Step by step

1. **Dashboard, as admin: Servers → Create SSH key.** Copy the `ssh-ed25519 …` line.
2. **Copy the `server` folder** from this package to the server, e.g. `/root/cc-gate-setup/`.
3. **Install, as root on the server:**

   ```sh
   cd /root/cc-gate-setup
   sh install-gate.sh --public-key "ssh-ed25519 AAAA... infinite-command-center"
   ```

   It creates the account, installs `cc-gate` and `cc-site-helper` (owned by
   root), writes `/etc/cc-gate/config.json` from the example if there is none,
   writes the sudo rules (checked with `visudo` before they are installed), and
   prints the server's **host key fingerprints**. Note them.
4. **Edit `/etc/cc-gate/config.json`:** one entry per WordPress site:

   ```json
   "sites": {
     "acme": { "path": "/home/acme/public_html", "user": "acme", "url": "https://acme.com" }
   }
   ```

   `user` is the CWP account that owns the site's files; `url` is the address
   `repair_restore_site_url` restores. Keep `"allow_changes": false` for now.
   List only the services you want visible, and in `restartable_services` only
   those you want the Command Center to be able to restart (empty = none).
   Then run `sh install-gate.sh --sync-sites` (sudo rules and backup folders).
5. **Dashboard: Servers → Add server** (host, port, account `ccagent`,
   environment `production`). Open it, **Scan host key**, compare the
   fingerprint with the one from step 3, and click **trust** only if they match.
6. **Test connection.** You should see `cc-gate 1.0.0 as ccagent (uid …)` and your sites.
7. **Websites → open a site → Server link (admin):** choose the server and the
   site key from step 4. Run **Run server-side check**.
8. When you are ready for repairs, set `"allow_changes": true` on the server.
   Every repair still waits for approval; production ones need an admin who
   types the site's name.

## Undo / remove

- Switch changes off again: `"allow_changes": false` (takes effect immediately).
- Take the Command Center's access away: `sh install-gate.sh --remove` (removes
  the key, sudo rules and programs; keeps the config, logs and backups), then
  `userdel -r ccagent` if you want the account gone.
- Database backups made before repairs are in `/var/lib/cc-gate/backups/<site>/`
  (owned by the site's user). Restore one with
  `sudo -u <site user> wp --path=<site path> db import <file>`.

## What was tested, and where

Everything above was tested in the developer's cloud sandbox against a
disposable WordPress container running real OpenSSH, sudo, WP-CLI and cc-gate
installed by `install-gate.sh` (Alpine Linux). It has **not** been run on a CWP
server yet. Operations that download from WordPress.org (core checksum check,
core reinstall, plugin update/reinstall) could not be exercised there, because
the sandbox cannot reach WordPress.org; they are implemented and their failure
handling is tested, but their success path is unverified until they run on a
real server.
