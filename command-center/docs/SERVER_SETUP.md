# Connecting a CWP server (restricted SSH)

The **VPS & Server Management** and **WordPress Security & Repair** agents reach a
server over SSH, but only through **cc-gate**: a small program that is the *forced
command* of a dedicated, unprivileged account. Whatever the Command Center asks
for, the server runs cc-gate, and cc-gate only performs operations from a short
allowlist, with checked arguments, without a shell.

Nothing in this guide is done for you. You run every step on your own server,
and you decide when (or whether) changes are allowed.

## What the Command Center can and cannot do

| | |
|---|---|
| Account | a dedicated account (default `ccagent`), never root; key login only |
| Key | an Ed25519 key generated by the Command Center; the private half stays encrypted in its database and is never shown, logged or sent to an AI model |
| The key can only run | `cc-gate` (`command="/usr/local/bin/cc-gate",restrict`): no shell, no port forwarding, no SFTP/SCP, no agent or X11 forwarding |
| Read operations | system overview (uptime, load, memory, disk), service status, WordPress version, core checksum check (including files that should not be there), plugin/theme lists with updates (must-use plugins and drop-ins included), administrator and super-admin accounts (and, listed apart, from WordPress 5.9, users of any other role that can manage options or promote users), home/siteurl, maintenance mode, debug.log presence |
| Change operations (only if you set `allow_changes: true`) | database backup, restore home/siteurl to the URLs in **your** config, deactivate/activate a plugin, update a WordPress.org plugin to the exact version the Command Center names, which is the approved one (cc-gate 1.2.0 refuses an update without a version, an older or the same version, any version other than WordPress.org's current release, and plugins that declare another update source; it fails if the plugin is any other version afterwards). The gate cannot see the approval itself, reinstall a WordPress.org plugin's files (refused for plugins that declare another update source), reinstall core files (same version), maintenance mode, cache and rewrite-rule flush, move debug.log into the backup folder, restart a service you listed as restartable |
| Never | run arbitrary commands, edit files, delete anything, read wp-config.php or the database, touch sites you did not configure, use root, run a site as root or as the gate account |
| Approvals | every change waits for a person's approval in the dashboard; for production sites or servers an **admin** must type the site or server name. The approval is checked again when it is decided and just before the change runs: if the site or server has been re-linked, renamed or moved to production since the request, the change is refused and must be requested again |
| Audit | every request is recorded in the Command Center (CWP / Servers page) and in `/var/log/cc-gate/gate.log` on the server |
| Time limits | each operation has a budget on the server (`timeout_seconds`, default 120 s; `slow_timeout_seconds`, default 600 s, for backups, downloads, checksum checks and debug.log moves). When it runs out, the program is asked to stop and then killed, and the change is reported as **outcome unknown** (critical event): check the site |

WP-CLI runs as each site's own system user through `cc-wp`, a small root-owned
program that is the only WP-CLI command in the sudo rules. It gives WP-CLI an
empty environment, a fresh temporary home, no file cache, and no WP-CLI packages
or global or user configuration, none of them in a folder the site user can
write, so files in the site user's home (`~/.wp-cli`) cannot change what WP-CLI
does. Plugins and themes are skipped where possible, so a broken
plugin cannot block a repair.

**What a hacked site can still influence.** Whenever WP-CLI loads WordPress
(plugin lists, administrator accounts, home/siteurl, maintenance mode), the
site's own `wp-config.php`, must-use plugins and drop-ins run, and malware there
can hide things from those answers. The core checksum check runs before
WordPress loads, so it does not depend on the site's code. Treat a clean
server-side check of a site you suspect as a good sign, not as proof.

## Requirements on the server

- EL8/EL9 (AlmaLinux, Rocky) with CWP, root access for the one-time setup.
- Python 3.6 or newer (always present on EL8/9 as `/usr/libexec/platform-python`).
- WP-CLI at `/usr/local/bin/wp` (install it once if missing:
  `curl -o /usr/local/bin/wp https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar && chmod 755 /usr/local/bin/wp`)
  and a PHP CLI on the PATH that WP-CLI can use.
- Your Command Center's public IP allowed to reach SSH (CSF: `csf -a <ip>`).
- Recommended sshd settings: `PasswordAuthentication no`, `PermitRootLogin no`
  (or `prohibit-password`), and if you use `AllowUsers`, add `ccagent`.

## Step by step

1. **Dashboard, as admin: Servers → Create SSH key.** Copy the `ssh-ed25519 …` line.
2. **Copy the `server` folder** from this package to the server, e.g. `/root/cc-gate-setup/`.
3. **Install, as root on the server:**

   ```sh
   cd /root/cc-gate-setup
   sh install-gate.sh --public-key "ssh-ed25519 AAAA... infinite-command-center"
   ```

   It creates the account, installs `cc-gate` and `cc-site-helper` (owned by
   root), writes `/etc/cc-gate/config.json` from the example if there is none,
   writes the sudo rules (checked with `visudo` before they are installed), and
   prints the server's **host key fingerprints**. Note them.
4. **Edit `/etc/cc-gate/config.json`:** one entry per WordPress site:

   ```json
   "sites": {
     "acme": { "path": "/home/acme/public_html", "user": "acme", "url": "https://acme.com" }
   }
   ```

   `user` is the CWP account that owns the site's files (never root or the
   `ccagent` account: the installer writes no sudo rules while a site uses it,
   by name or uid); `url` is the address `repair_restore_site_url` restores.
   If WordPress lives in its own folder (WordPress address differs from the site
   address), also set `"siteurl": "https://acme.com/wp"`. Without it, a
   WordPress address like that for a site whose `path` ends in `/wp`, below a
   folder inside the site user's home (such as `/home/acme/public_html/wp`), is
   reported as a probable subdirectory install. Restoring the addresses then
   leaves that siteurl as it is: a changed home is still restored, but while home
   is right the restore is refused until you set `siteurl`. Keep
   `"allow_changes": false` for now.
   List only the services you want visible, and in `restartable_services` only
   those you want the Command Center to be able to restart (empty = none).
   Then run `sh install-gate.sh --sync-sites` (sudo rules and backup folders).
5. **Dashboard: Servers → Add server** (host, port, account `ccagent`,
   environment `production`). Open it, **Scan host key**, compare the
   fingerprint with the one from step 3, and click **trust** only if they match.
6. **Test connection.** You should see `cc-gate 1.2.0 as ccagent (uid …)` and your sites.
7. **Websites → open a site → Server link (admin):** choose the server and the
   site key from step 4. Run **Run server-side check**.
8. When you are ready for repairs, set `"allow_changes": true` on the server.
   Every repair still waits for approval; production ones need an admin who
   types the site's name.

## Updating cc-gate

Run `sh install-gate.sh` from the `server` folder of the new Command Center
version, as in step 2; your `/etc/cc-gate/config.json` is kept. **Test
connection** then shows the new version. The Command Center flags an older
gate ("gate_outdated"), and it sends no plugin update to a gate older than
1.2.0, because only 1.2.0 and later install exactly the approved version (and
only WordPress.org's current release, never an older one).

## Undo / remove

- Switch changes off again: `"allow_changes": false` (takes effect immediately).
- Take the Command Center's access away: `sh install-gate.sh --remove` (removes
  the key, sudo rules and programs; keeps the config, logs and backups), then
  `userdel -r ccagent` if you want the account gone.
- Database backups made before repairs are in `/var/lib/cc-gate/backups/<site>/`
  (or the `backup_dir` you set; owned by the site's user). Restore one with
  `sudo -u <site user> wp --path=<site path> db import <file>`.
- If a repair fails part-way, the dashboard raises a critical `repair.failed`
  event with what was done, the backup file and whether the site still loads.

## What was tested, and where

Everything above was tested in the developer's cloud sandbox against a
disposable WordPress container running real OpenSSH, sudo, WP-CLI and cc-gate
installed by `install-gate.sh` (Alpine Linux). It has **not** been run on a CWP
server yet. Operations that download from WordPress.org (core checksum check,
core reinstall, plugin update/reinstall) could not be exercised there, because
the sandbox cannot reach WordPress.org; they are implemented and their failure
handling is tested, but their success path is unverified until they run on a
real server.
